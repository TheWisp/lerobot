## Current conclusion

There are at least two failure modes, not one:

1. The 0803 30k policy rapidly moves toward a learned posture and then stays or
   oscillates around that region. The control loop is running and commands are
   reaching the robot; this is a policy attractor, not a frozen process.
2. The 0805 1k policy emits very rough chunks and large frame-to-frame action
   changes. It was sufficiently unsafe that the operator stopped it.

Unsafe position normalization is a proven causal contributor to the old
checkpoints, but the normalization-only 0803 retrain has now falsified it as
the sole cause of the current physical failures:

- The new 0803 30k checkpoint no longer has the extreme left-position input
  gain, yet eleven physical runs still include posture attraction and
  occasional malformed action chunks.
- The 0803 attractor remains consistent with absolute-action training on a
  narrow set of bimanual postures and with insufficient task coverage.
- The 0805 1k checkpoint is visibly undertrained. Its exact in-distribution
  chunk is substantially rougher than the 5k and 10k checkpoints.
- The confirmed episode-boundary bug corrupts all of these Flow S1 runs and is
  an additional source of degraded chunks.

The new 30k runs also expose two runtime effects that are independent of the
position floor. First, discarded cold-start inference latency pollutes RTC's
rolling delay estimate, so the first live replans use a six-frame prefix while
the measured inference itself takes about one frame. Second, the query-interval
sleep is added after inference rather than scheduling inference start-to-start;
an interval of five therefore publishes about every six to seven control
frames and executes deeper into any malformed chunk.

For both old and new 0803 oscillation, the proximate source is the policy
command stream rather than the motor layer. In the old checkpoint, malformed
live-state normalization interacting with fresh Flow sampling was sufficient
to turn a smooth fixed-frame chunk into rough, seed-sensitive chunks. In the
new treatment checkpoint that specific gain is gone, while live reversals
remain. The remaining causal split is now between startup RTC contamination,
live visual/state distribution shift, episode-boundary corruption, stochastic
mode switching, and action/data coverage.

Normalization was causal in the old checkpoint, not merely correlated:
changing only a near-constant left-arm position changed predicted right-arm
chunks by tens of degrees under a fixed image, fixed remaining state, and fixed
Flow seed. The new retrain is the negative control showing that mechanism no
longer explains today's full symptom.

learned weights. The historical value was 100, but executing all 100 predicted

100-frame ACT baseline is established.

This is not a perfect normalization control. ACT currently maps both STATE and
ACTION to mean/std normalization through the generic processor, whose scale is
`std + 1e-8`. The 0805 dataset contains left-arm position standard deviations
as small as about 0.0007 degrees, so ACT can also amplify small live-state
offsets. Therefore: a successful ACT rollout is strong evidence against the
dataset and toward an HVLA-specific failure; a failed ACT rollout is ambiguous
between dataset/coverage, shared normalization, and architecture. Analyze ACT
chunks on recorded dataset frames before interpreting a physical rollout.

## Near-constant state normalization

Flow S1 independently implements z-score normalization:

```python
state_std = all_states.std(dim=0).clamp(min=1e-6)
normalized_state = (state - state_mean) / state_std
```

The older dataset varies both arms. The two recent datasets keep several left
dimensions nearly or exactly constant:

| Dataset | State dimensions with std below `1e-3` | Action dimensions stored at `1e-6` |
|---|---:|---:|
| Older | 0 | 0 |
| 0803 | 3 | 4 |
| 0805 | 3 | 6 |

Examples:

- 0803 `left_joint_3.pos` has one unique raw value and stored std `1e-6`.
- 0805 `left_joint_4.pos` has one unique raw value and stored std `1e-6`.
- A `0.001°` runtime discrepancy therefore becomes a normalized change of
  approximately 1,000.

The training loader never presents those values. Training absolute-z p99 is
only about 3.5 for 0803 and 2.9 for 0805. Low training loss and ordinary gradient
norms therefore do not test the deployed model's derivative in these unseen
state directions.

This is the same failure class addressed for LeRobot quantile normalization by
**“Fix normalization when value is too small” — January 12, 2026**. Flow S1's
later private normalizer bypassed that shared protection.

### What the earlier Pi0.5-era fix actually did

The January 12 change did **not** add OpenArm-wide calibration statistics and
did not remove stationary joints. Pi0.5 already selected dataset-local
`QUANTILES` normalization for both state and action. The shared normalizer was
changed as follows:

```python
range = q99 - q01
effective_range = where(abs(range) < 0.1, 1.0, range)
normalized = 2 * (value - q01) / effective_range - 1
normalized = clamp(normalized, -10, 10)
```

The same `effective_range` is used by the inverse action transform. Thus a
nearly stationary dimension remains in the model contract, but its small
empirical spread cannot become an arbitrarily large gain. The required q01/q99
values already live in each LeRobot dataset's `meta/stats.json`; no additional
robot-wide dataset is required.

That hard-coded `0.1 -> 1.0` rule is evidence for the safety invariant, not
necessarily the final threshold for Flow S1. Flow S1 mixes position, velocity,
and torque in one vector, so a production implementation should use documented
per-feature-group scale floors in the corresponding physical units. The
January 12 change also added no regression test, so its exact constants should
be treated as a pragmatic historical fix rather than a fully verified standard.

### Selecting a position scale floor

OpenArm follower observations expose joint position in degrees. The Damiao
feedback packet encodes position with 16 bits over `[-12.5, 12.5]` radians, so
one reported-position quantum is approximately `0.0219°`.

For the 0803 dataset, the left-arm joint-position statistics are:

- empirical standard deviation: `0–0.109°`;
- q01-to-q99 range: `0–0.393°`;
- within-episode frame-to-frame p99: at most one feedback quantum (`0.0219°`).

The moving right-arm joint-position standard deviations are `7.53–25.44°`.
Therefore an initial Flow S1 z-score rule of

```python
effective_position_std = maximum(empirical_position_std, 0.5)  # degrees
```

stabilizes only the low-motion position dimensions. Under this rule, a feedback
quantum is `0.044` normalized units, `0.1°` is `0.2` units, and `0.001°` is
`0.002` units instead of `1,000` units. For a `2 * (x - q01) / range - 1`
quantile transform, the equivalent minimum range is `1.0°`.

`0.5°` is a baseline to verify, not a universal constant. It is close to the
original ACT qpos/action floor of `0.01 rad` (`0.573°`) and to the effective
scale of the earlier Pi0.5 fallback. The final value should be checked using a
torque-on stationary capture at several safe postures:

1. Measure per-joint p99 absolute idle deviation and command-tracking error.
2. Choose a floor large enough that idle deviation stays below a chosen
   normalized budget (for example `0.2–0.25`).
3. Check that the smallest task-relevant angular change remains visible to the
   model. A floor is a scale, not a deadband: `0.1°` remains distinguishable.
4. Sweep at least `0.25°`, `0.5°`, and `1.0°` offline, retrain, and require
   bounded action-chunk changes under `±0.022°`, `±0.1°`, and `±0.5°` state
   perturbations before hardware evaluation.

State and action floors should be separately configurable even if `0.5°` is
the first candidate for both. The action floor also determines how normalized
prediction error becomes physical command error, so it requires chunk-level
output and motion-guard validation.

### What is known about the 0803 oscillation

The oscillatory command is already present before the motor driver. The two
0803 30k application logs contain 24 and 20 policy-command jumps in roughly
five to six seconds, including commands that alternate by more than `10°` on
successive steps. The logged predicted chunks themselves alternate, so this is
not explained solely by mechanical tracking or motor-controller tuning.

Flow inference starts each new chunk from fresh Gaussian noise, and the 0803
GUI run queried the model every two control frames. A 16-seed fixed-observation
test gives:

| 0803 input | Mean right-chunk roughness | Mean right-output std across seeds |
|---|---:|---:|
| Exact dataset frame | `0.319°` | `0.560°` |
| Only left positions replaced by matching logged values | `3.422°` | `3.139°` |

With a six-action RTC prefix, the exact input has a mean prefix-to-tail jump of
`0.340°` (`1.026°` maximum). The logged-left input raises that to `4.034°`
mean and `21.551°` maximum; its generated suffix remains rough (`3.320°`).
Thus fresh Flow noise is comparatively benign on the exact training input but
is strongly amplified by the malformed live state. RTC preserves the committed
prefix exactly, but cannot make the newly generated tail smooth under that OOD
conditioning.

This establishes a proximate mechanism capable of producing the observed
back-and-forth commands: tiny/live left-state differences become extreme model
conditioning, repeated stochastic replanning produces substantially different
rough chunks, and the controller executes their prefixes. It does not yet prove
that normalization is the sole cause of the closed-loop physical symptom. The
test substitutes rounded logged left positions into a dataset frame rather than
reconstructing every raw live scalar and image, and no checkpoint has yet been
retrained with one defect fixed at a time.

The attractor location is a separate aspect: absolute-action demonstrations
concentrated at one left posture explain why the policy drives toward the
dataset action mean. The episode-boundary bug can further degrade chunk
smoothness. Their relative contributions require a controlled retraining
matrix: original, normalization-only fix, boundary-only fix, and both fixes,
evaluated on identical frame sequences and state perturbations before hardware.

### Normalization-only retrain protocol

The first causal retrain deliberately changes only the effective scale of named
position observations. It does **not** change action normalization, episode
boundaries, action representation, RTC, the model, or the dataset:

```text
control:   state_position_std_floor=0.0°, seed=1337
treatment: state_position_std_floor=0.5°, seed=1337
```

Both are fresh 0803 trainings with the original architecture and schedule:
50-action chunks, 15 flow steps, RTC delay 6/drop 0.2, 224x224 images,
768 hidden width, 6 decoder layers, batch 128, and the original 50,000-step
schedule. The causal comparison is made at matching checkpoints, especially
30,000 steps; keeping the 50k scheduler horizon makes the 30k learning rate
match the original run. Explicitly seeding Python, NumPy, PyTorch, CUDA, the DataLoader
sampler, and workers holds initialization and sample order as closely as the
CUDA kernels permit. The pre-existing 30k checkpoint remains useful context,
but it was trained without a recorded seed and is not a strict paired control.

The opt-in prototype keeps the legacy default at `0.0`, identifies position
features from the dataset's ordered names ending in `.pos`, and saves the
chosen floor in both checkpoint and training metadata. On the real 0803
dataset, `0.5°` floors all eight left position scales (`0–0.109°`) and none of
the eight right position scales (`7.53–25.44°`). Recomputed action means and
standard deviations are bit-identical to the old checkpoint.

The implementation regression test was first run against the old trainer and
failed because the floor did not exist. After the prototype, targeted tests
cover selective feature application, unchanged action normalization, legacy
behavior, ambiguous feature-order rejection, checkpoint round-trip, and the
GUI-command-to-trainer-parser boundary.

#### Why the first treatment floors state but not action

State and action position fields use the same physical unit, but their scales
sit on opposite sides of the policy:

```text
state input:       normalized = (measured_position - mean) / scale
action output:     command = predicted_normalized_action * scale + mean
```

Increasing the state scale reduces the gain from sensor/posture mismatch.
Increasing the action scale increases the physical motion caused by a given
normalized prediction error. They therefore should not be tied to one knob
merely because both are angles.

In 0803, four left action scales are exactly `1e-6°`, the other four are
`0.046–0.110°`, and right action scales are `7.54–25.82°`. Exact constant
action targets normalize to zero, and the tiny inverse scale suppresses rather
than amplifies their physical prediction error. The RTC prefix is sliced from
the previously predicted raw chunk and normalized with the same saved action
statistics, so it also round-trips through the same scale; it is not a raw
motor-feedback mismatch analogous to state.

Action normalization is not thereby declared correct. Standardizing small
recording noise to unit variance can overweight inactive action channels in the
training loss and shared decoder gradients. Conversely, blindly replacing an
action scale of `1e-6°` with `0.5°` can turn a normalized residual into real
left-arm jitter. A separate action-only A/B must inspect per-dimension loss,
normalized residuals, denormalized chunks, and RTC prefixes, and its floor must
be selected from acceptable command error rather than sensor input noise.

The current state-only treatment is consequently an identification experiment:
the prior ablation changed only state and moved right-arm outputs by tens of
degrees. If the retrain removes that gain while action statistics remain
bit-identical, it directly attributes that mechanism to state normalization.
Changing both scales in the first run would make any improvement ambiguous.

Checkpoints must pass these hardware-free gates before a guarded rollout:

1. Exact held-out 0803 frames produce finite, reasonably smooth chunks.
2. Replacing dataset left positions with matching logged values no longer
   amplifies right-arm chunks by tens of degrees.
3. Perturbations of `±0.022°`, `±0.1°`, and `±0.5°` have bounded output gain
   across multiple Flow seeds, including with a six-action RTC prefix.
4. Treatment improves those metrics relative to its paired control without a
   material regression on ordinary in-distribution chunks.

Passing these gates would prove the normalization defect causes the excessive
state sensitivity and establish whether it explains the oscillatory mechanism.
It would not prove that posture attraction or missing task coverage is solved.
If normalization improves the intended measures, the next isolated A/B is the
episode-boundary fix; if not, the same paired checkpoints still falsify the
normalization-only explanation cleanly.

### Feeding exact training frames into the new checkpoint

Seven selected 0803 frames were decoded from all three training videos and fed
directly to the new 30k checkpoint with the saved raw 48-dimensional state and
no S2 token, matching the GUI's `--zero-s2` path. The set includes episode
start, real gripper opening and closing transitions, frames nearest three
logged interval-5 poses, and a sample whose 50-token training target was
boundary-affected. Each was tested across eight Flow seeds with no prefix and
with exact two- and six-action RTC prefixes.

The result is not “the checkpoint always emits nonsense.” Stable exact frames
have first-ten-token target MAE of roughly `0.1–0.7°`; RTC prefixes reduce
seed variation and are preserved. At real demonstrated gripper transitions,
the model reproduces large but predominantly one-direction motion, for example:

```text
target:    -11, -32, -39, -45, -45, ...
prediction: -8, -40, -44, -44, -45, ...
```

A second stratified check used 32 random exact training frames, four Flow seeds
per frame (128 chunks per condition). In the first 20 tokens, 22.7% of
no-prefix chunks and 24.2% of two-frame-RTC chunks contain a gripper step over
`10°`, consistent with the deliberately sharp demonstrated gripper commands.
None of the 256 chunks contains large jumps in both directions.

That negative control matters because live malformed chunks do reverse. One
interval-5 example is:

```text
-28, -24, -23, -10, -4, -3, -25, -32, ...
```

Across the correct 0803 labels, only 6 of 40,101 possible eight-token chunks
(`0.015%`) contain `>10°` gripper events in both directions. Reversal is
therefore not a normal short-horizon target pattern merely hidden in a low
aggregate training loss.

### Cold-start RTC contamination

All four runs with an initial gripper-jump burst show the same sequence:

```text
first real inference: expected_d=0 actual_d=22, infer about 730 ms
fresh episode chunk:  expected_d=0 actual_d=1
next replans:         expected_d=6 actual_d=1, prefix_len=6
steady state:         expected_d=2 actual_d=1, prefix_len=2
```

The first slow chunk is produced before the episode, then deliberately
discarded when the episode requests a fresh observation. Its roughly
`0.74 s` delay nevertheless remains in `InferenceThread.inference_delays`.
The next RTC estimate takes the arithmetic mean of that history and clamps to
the configured maximum of six frames. Thus an initially poor unprefixed live
chunk is committed and copied farther than actual latency requires. Every
early violent jump in `run_20260805_113412.log`,
`run_20260805_113459.log`, `run_20260805_114258.log`, and
`run_20260805_114444.log` occurs during this startup-contaminated period.

This is a proven runtime defect and a plausible amplifier of the beginning
failure, not proof that the underlying initial chunk is good. A correct fix
must exclude discarded/warm-up inferences from the live RTC estimator (or
explicitly reset and seed the estimator at episode activation), then test that
the first live prefix matches measured total delay.

The query interval has a separate semantics mismatch. The UI describes an
interval of `N` as inference every `N` policy steps, and the latency budget uses
`fps/N`. The thread currently sleeps the full `N/fps` *after* inference. At
30 fps, interval 5 plus a roughly 30–40 ms inference yields an observed
`exec_idx` of 6–7, not 5; interval 2 yields 3–4, not 2. The scheduler should be
measured start-to-start if the UI and monitoring contract is retained.

Neither runtime defect explains the full late/stuck symptom. The step-1309
burst happens at steady `expected_d=2`, and a posture attractor can be smooth.
The next discriminating artifact is a short GUI run recorded as a LeRobot

### Successful live diagnostic rollout at 12:33

`run_20260805_123329.log` is the first complete diagnostic episode. It saved
673 frames over 24.4 seconds and finalized
`debug/new30_i5_diag_20260805_03` with one episode. Despite the `_i5` name, the
effective launch used **query interval 2**, not 5; the log states
`Query interval = 2 steps (67ms)`. The configured episode duration was 60
seconds, and the operator stopped after 24.4 seconds.

The recorded action column and runtime log agree exactly on the gross failure:
there are 27 adjacent commands above 10 degrees, all on
`right_gripper.pos`. They occur in three bursts at control steps 1–75,
203–228, and 269–281. The other right-arm joints have maximum adjacent command
changes of 1.4–4.6 degrees; left-arm commands are effectively stationary.
The right gripper spans approximately `-45.47` to `+0.83` degrees.

The inference-side capture saved 29 chunks whose first 20 tokens contain a
step above 10 degrees; every one names the right gripper as the worst output.
Eleven of those 29 chunks contain large gripper steps in both directions in
the first 20 tokens. This malformed trajectory exists before motor tracking,
so the executed oscillation is not explained by CAN feedback or follower
tracking error.

The live normalized state is numerically out of distribution in left-arm
torque: after motion starts, `left_joint_3.torque` is the largest feature in
27/29 captured chunks, reaching `|z|=32.94`. This is a limitation of the
position-only normalization prototype, but a paired-input causal replay rules
it out as the main gripper-oscillation cause. On five captured observations
and eight fixed Flow seeds each, centering only left joint 3 torque, all left
torques, all torques, or clipping torque z-scores to ±5 leaves the bad-chunk
count at 38/40 in every condition. Aggregate right-gripper changes from the
unaltered live-state output are only about 0.22–0.27 degrees when left torque
is centered.

RTC prefix conditioning is a much stronger causal amplifier. Six captured
observations were replayed with 16 paired Flow seeds. Metrics exclude deltas
wholly inside the copied prefix but retain the prefix-to-new-prediction
boundary. With no prefix, 45/96 chunks have a >10-degree gripper step and
8/96 contain large steps in both directions. With the exact captured prefix,
those counts rise to 91/96 and 51/96 respectively; median first-20-token total
variation rises from 44.7 to 73.9 degrees. Thus RTC propagates and magnifies an
existing live gripper transition into back-and-forth motion. It is not the
sole origin: the fresh episode chunk has no prefix and already contains a
14.2-degree one-way step, and the no-prefix live replay still has 45/96 rough
chunks.

The 0803 labels explain sharp *one-way* gripper changes but not frequent live
reversals. There are 749 within-episode adjacent right-gripper label changes
above 10 degrees; 21.32% of correctly clipped 20-token training targets
contain at least one. Only 36/40,101 correct 20-token targets (0.09%) contain
large steps in both directions. The confirmed boundary bug does not create a
direct right-gripper discontinuity at episode joins (the 240 joins are
normally `-45 -> -45`). Over the full 50-token target, however, crossing into
the next episode adds 694 rough windows and 407 bidirectional windows, so it
can teach a rare close-then-reopen mode and still requires a clean retrain.

Finally, synchronous JPEG/NumPy diagnostic writes occur in the inference and
control threads. They do not alter tensor values already produced, but they
can alter scheduling and chunk indices; the first episode chunk advanced to
index 12 by control step 1. The capture is therefore valid for offline chunk
causality but not a timing-neutral benchmark. Future live capture should queue
writes to a background writer or retain only bounded in-memory snapshots.

### Focused interpretation of the proposed hypotheses

The useful parts of the proposed investigation are already partly resolved:

- Feeding exact 0803 training frames into the 30k checkpoint is a strong
  negative control. Across 32 frames, four Flow seeds, and both no-prefix and
  RTC-prefix conditions, none of 256 chunks had the bidirectional large-jump
  pattern seen live. The checkpoint can reproduce clean chunks on its training
  distribution.
- Capturing the live chunk at the point of failure was also necessary. The
  successful rollout proves that the repeated motion is present in the policy
  output, before the motor driver, and is concentrated in
  `right_gripper.pos`.
- A broad "the demonstrations contain too much waiting" explanation is not
  supported by the action labels. Only 726/40,101 correctly clipped 50-frame
  targets (1.81%) have less than one degree of right-arm path length, and these
  are concentrated in the final 10% of task progress. There are only two
  simultaneous arm-and-gripper hold runs of at least 0.5 seconds, both near the
  episode end. Removing low-displacement chunks would mostly remove valid
  terminal holds and would bias the policy against stopping.
- State/action ambiguity or insufficient visual coverage remains plausible,
  because exact training inputs are clean while saved live inputs are rough
  even without a prefix. It is not yet proven; the next offline test for that
  branch is image/state nearest-neighbour retrieval followed by measuring
  disagreement among the neighbours' future action chunks.
- The proposed feedback trap is supported in a more specific form: it is not
  evidence that the model generally learns to get stuck after predicting a
  hold. The paired replay shows that RTC conditioning copies a bad old
  trajectory into the next inference and raises bidirectional gripper failures
  from 8/96 to 51/96.

SARM and RABC are outside the scope of this investigation. No recommendation
here depends on either method.

### RTC uses inconsistent time origins

There is a second concrete RTC defect beyond cold-start history leakage. The
runtime takes the old-chunk execution index only *after* preprocessing the
observation and records that moment as `t_exec_idx`. It then:

1. slices `old_chunk[exec_idx : exec_idx + expected_d]`;
2. estimates `expected_d` from `t_infer_end - t_obs`, which starts earlier,
   before preprocessing; and
3. publishes the returned chunk with position zero anchored at `t_exec_idx`.

Those quantities cannot all describe the same timeline. With the current
`t_exec_idx` origin, the copied prefix begins at `t_exec_idx`, so its required
length is the delay from `t_exec_idx` until publication. Instead the code uses
the longer observation-to-publication delay. In the live log this commonly
produces `expected_d=2` while inference itself advances only one 30 Hz frame;
the cold-start-contaminated case produces `expected_d=6` while only one or two
frames advance. The alternative valid formulation would anchor both the old
chunk slice and the new chunk at `t_obs`; the implementation does not do that
either.

The forward-looking prefix and mixed timebase were introduced by
**"fix(hvla): correct RTC prefix to use upcoming actions, unify time-shift
indexing" — March 17, 2026** and **"fix(hvla): correct RTC chunk indexing and
add S2 GPU throttle" — March 17, 2026**. Extraction into `InferenceThread` on
March 22 moved the logic without changing that contract. This is local HVLA
runtime code, not a general LeRobot inference path.

This proves a scheduling/alignment defect, while the paired replay proves that
the prefix is a major oscillation amplifier. It still does not prove that RTC
creates the first bad live chunk: no-prefix live replays remain rough. The safe
next order is therefore (a) make capture timing-neutral, (b) add a runtime RTC
A/B switch and correct/reset its timing state, (c) replay the saved inputs
offline, and only then (d) perform a short, guarded hardware A/B rollout.

### RTC repair prototype and reconstructed-prefix replay

The local inference prototype now makes four independently testable changes:

1. Runtime RTC can be disabled without changing the checkpoint. The GUI field
   is **RTC Prefix** and the CLI boundary is `--disable-rtc-prefix`.
2. An observation snapshots the old chunk and computes its prefix start from
   that old chunk's origin at `t_obs`. The returned chunk is also anchored at
   `t_obs`; a mutable main-loop index from a different chunk generation is no
   longer mixed in.
3. Episode/intervention reset clears chunk, observation, execution-index and
   latency history. A generation guard discards an inference that began before
   reset but completed afterward.
4. Query interval is scheduled start-to-start, so interval 5 means five 30 Hz
   steps rather than inference time plus five steps.

Because the old capture did not save the old chunk origin, its corrected prefix
can only be reconstructed approximately. Six captures with a saved immediately
preceding chunk were replayed for 16 paired seeds. The old execution index was
back-projected by the recorded preprocessing delay and the prefix length was
set from total observation-to-result delay:

| Prefix mode | `>10°` gripper chunk | Bidirectional `>10°` | Median TV |
|---|---:|---:|---:|
| none | 36/96 | 12/96 | 41.7° |
| captured old runtime | 92/96 | 39/96 | 66.7° |
| approximately observation-aligned | 67/96 | 28/96 | 67.1° |

Correct alignment reduces failure substantially relative to the old prefix but
does not make prefix conditioning safe, and it remains worse than no prefix.
This is why the first guarded hardware comparison should keep an explicit RTC-
off arm rather than testing only the repaired timing.

### The first bad chunk is visually triggered, not state-triggered

The fresh live episode chunk (`infer_drop_2`) has no prefix. Its right gripper
starts near `-36°` and opens to approximately zero within ten tokens. Across 64
fixed Flow seeds, 58/64 chunks contain a `>10°` gripper step, but none contains
large changes in both directions. This is the seed trajectory that RTC later
turns into reversal.

Counterfactual replacement isolates the relevant input branch. Keeping the
exact live camera frames while replacing only right-gripper position, every
joint position, or the complete 48-D state with the nearest training episode-
start state leaves the result unchanged: 58--59/64 rough chunks and less than
about `0.2°` change in aggregate gripper metrics. Thus neither the left-arm
position nor the normalized state is the proximate trigger for this first
chunk.

Per-camera replacement on the same input is decisive (32 paired seeds):

| Input | `>10°` chunks |
|---|---:|
| original live cameras | 29/32 |
| replace left wrist with training start | 29/32 |
| replace top camera with training start | 21/32 |
| replace right wrist with training start | 0/32 |
| replace all cameras with training start | 1/32 |

The effect generalizes beyond the first burst. On six early/late captures and
16 seeds, all evaluated without RTC, live inputs produce 45/96 rough and 12/96
bidirectional chunks. Replacing only the right-wrist image with the image from
the position-nearest training frame reduces this to 1/96 and 0/96; replacing
only top reduces it to 17/96 and 3/96; left-wrist replacement leaves 39/96 and
14/96. These are artificial counterfactuals and not a deployable fix, but they
prove that the right-wrist visual condition is causal for the malformed chunk.

At the live start the top camera sees the orange ball, while the right-wrist
camera sees the bin rim/background and no ball. The nearest training episode
start used in the counterfactual has the ball filling a large part of the
right-wrist view. This does not prove that ball visibility alone is the learned
feature; wrist pose, crop and scene geometry all change together. It does prove
that changing this camera while holding state and the other two images fixed
removes the failure.

An approximate visual-coverage audit used the checkpoint's own DINO
backbone on `top + right_wrist`, with 4,011 uniformly sampled training frames.
Training nearest-neighbour distance was measured only across different
episodes, avoiding near-duplicate temporal neighbours. The 29 captured bad
inputs have a median training-distance percentile of 96.7 and a 90th
percentile of 99.5. The first two frames are less extreme (about the 79th
percentile); after the first erroneous movement, later frames move into the
94th--99.7th percentiles. This supports compounding visual covariate shift.

The nearest visual labels are also ambiguous: 14/29 captures have both open
and closed right-gripper actions among their top 20 visual neighbours. Flow S1
uses one current observation, not temporal image history. This checkpoint was
trained with `s2_latent_path=null`, and the live log explicitly says "Running
without S2 conditioning", so the GUI task prompt supplies no task-progress
signal to S1 in this run. Locally, replacing the complete state has negligible
effect, so state does not resolve the visual ambiguity at the failing input.

### The arm is also jittering even when its per-step magnitude looks modest

The 673-frame executed trajectory has right-arm total variation per frame that
is mostly within the demonstration range, but its direction changes are not.
After ignoring deltas below `0.2°`, each right arm joint reverses on 38--56% of
eligible steps; demonstration medians are 3--7% and 90th percentiles are
7--16%. The gripper reaches 63% versus an 11% demonstration median and 18% 90th
percentile. Therefore the observed "moving around the same spot" is measurable
chunk-to-chunk jitter, not merely a subjective description.

This also explains why increasing query interval can look better: it samples a
new stochastic Flow mode less often and executes more of one internally smooth
chunk. It is a symptom-reducing cadence change, not evidence that interval 5
fixes the visual ambiguity or RTC.

#### The live input follows visual pose and nearly ignores numerical state

The model remains accurate on exact training inputs. For training frame 0,
`right_joint_4` has a 30.2-degree label and a 29.7-degree median prediction;
median full-chunk MAE over 64 Flow seeds is about 0.37 degrees. Five other exact
training frames show similarly small errors. The checkpoint is therefore not
globally unable to reproduce its training chunks.

The new live start is nevertheless visually outlying. Using the checkpoint's
DINO features for `top + right_wrist`, its nearest cross-episode training-frame
distance is at the 91.9th percentile. Its visually nearest training labels keep
action near measured state; they do not contain the live 13-degree initial
elbow error.

Camera counterfactuals localize that error for this run. Across 64 paired Flow
seeds, the median first `right_joint_4` target is:

| Input | Median first target |
|---|---:|
| exact live images | 44.9 degrees |
| replace only live right wrist with training frame 0 | 43.2 degrees |
| replace only live top with training frame 0 | 33.6 degrees |
| replace all images with training frame 0 | 29.7 degrees |

Thus the large initial elbow target in this run is driven mainly by the top
view, not by right-wrist ball visibility. “Ball visible” is too weak a coverage
criterion: ball position/scale, arm geometry, crop, background, and task phase
jointly define the observation.

State counterfactuals expose a more structural problem. Replacing the complete
live 48-D state with training frame 0 changes normalized state by RMS 3.76
standard deviations, yet paired model outputs change by only about 0.01 degree
on average (less than 0.2 degree at the worst token). Replacing the images while
holding state fixed changes outputs by about 5.6 degrees on average. Training
frame 0 images produce essentially the training-frame action whether paired
with their real state or the inconsistent live state.

The architecture supplies 768 DINO patch tokens (256 for each camera) and only
one state token. On the exact live input, decoder cross-attention assigns the
state token only 0.03--0.12% mean mass across its six layers, at or below the
0.13% uniform-token baseline. The counterfactual output test, rather than
attention alone, proves the practical consequence: this trained checkpoint has
learned an almost image-only action mapping. The state-position normalization
floor does not repair a state branch that the policy does not use.

This also separates the role of normalization. The right-arm position scales
are 7.5--25.4 degrees and are unaffected by the 0.5-degree floor; only the
stationary left-position inputs were floored. All left-arm commands in this
rollout remain effectively constant. The floor removes the prior numerical
hazard, but it is not the cause or cure of the current right-arm oscillation.

#### Offline sequential RTC replay

The 133 saved observations allow a hardware-free continuity comparison. Eleven
observations at five-frame spacing were replayed for 32 paired Flow-noise
sequences. At each of 320 boundaries, the new token actually reached near
publication time was compared with the old chunk's continuation:

| Stitching mode | Boundaries over 10 degrees | Median max-joint gap | 90th percentile |
|---|---:|---:|---:|
| no prefix | 144/320 | 9.60 degrees | 20.73 degrees |
| observation-aligned 2-frame prefix | 48/320 | 3.77 degrees | 11.21 degrees |
| observation-aligned 3-frame prefix | 14/320 | 2.58 degrees | 8.03 degrees |

This explains the hardware A/B result. Disabling RTC removes the earlier bad
prefix behavior but also removes Flow S1's only intended continuity mechanism;
hard replacement every five frames is not a deployable fallback. Correctly
aligned conditioning is beneficial on this visible-ball trajectory, and a
conservative three-frame prefix is markedly better than two. It still does not
correct the first live target, and a few RTC-conditioned chunks retain greater-
than-10-degree internal `right_joint_4` steps. No further hardware rollout is
warranted until both initial-action safety and chunk continuity pass offline
gates.

A tempting first-chunk workaround is to construct an RTC prefix by repeating
the measured current joint pose. Offline replay rejects it. A two- or
three-frame repeated-pose prefix makes the first published token safe only
because that token is directly clamped, but every one of 128 paired samples
then has a greater-than-10-degree jump at the first unconditioned token (median
max-joint gap 35--39 degrees). Training RTC prefixes are moving demonstration
actions, not arbitrary hold poses; a synthetic hold prefix is out of
distribution and must not be deployed. Initial motion needs an external
trajectory-rate gate or a model trained with an explicit hold/start contract.

## The embodiment constraint

The full bimanual state and action contract must remain. A task episode in which
one arm does not move does not make that arm invalid or removable.

However, two separate facts must be handled:

1. A stationary feature must not acquire an arbitrarily large numerical gain.
2. A dataset containing only one left-arm posture cannot teach how desired
   behavior should vary over arbitrary left-arm postures.

The first is an implementation problem. The second is a coverage/action-
representation problem. Fixing normalization prevents catastrophic
extrapolation, but it cannot invent the missing dependency.

For absolute joint-position actions, “left arm did not move” means the target is
the same recorded pose at every frame. From a different initial pose, the learned
policy is therefore encouraged to return the arm to that recorded pose. If the
desired semantic is “hold the current left pose,” joint delta/residual actions
express it naturally: zero delta means hold wherever the arm currently is.

## Confirmed episode-boundary bug

`FlowMatchingDataset` builds boundary maps only if `LeRobotDataset` exposes an
`episode_data_index` attribute. LeRobot v3 datasets have an `episode_index`
column and no such attribute. The wrapper silently treats the entire dataset as
one episode, so 50-frame targets near an episode end contain the beginning of
the next episode and are not marked as padding.

The defect has existed in Flow Matching S1 since **“feat(hvla): swappable S1
with flow matching + training-time RTC” — March 16, 2026**. It is specific to
this custom wrapper, not LeRobot's native episode-aware dataset reader and not
all HVLA S1 implementations.

Directly invoking the real wrapper two frames before a boundary proves that the
third target is the next episode's first action and is unmasked. Installing only
correct episode boundaries into that same wrapper makes it repeat the current
episode's final action and mark padding, as does LeRobot's native reader.

| Dataset | Samples crossing boundaries | Wrong unmasked action tokens |
|---|---:|---:|
| Older | 20.4% | 10.2% |
| 0803 | 29.3% | 14.7% |
| 0805 | 25.4% | 12.7% |

This label corruption is serious, but it cannot alone explain the different
0803 and 0805 symptoms: the older model also had it and the input ablation above
isolates a second causal mechanism.

## Practices in other robotics stacks

### OpenPI

OpenPI does not fully auto-solve degenerate normalization. Its current normal
path divides by `std + 1e-6`, and its quantile path divides by
`q99 - q01 + 1e-6`. Its own troubleshooting guide now warns that rarely used
dimensions can produce tiny statistics and huge normalized states/actions, and
suggests manually correcting stats as a workaround.

OpenPI does provide two important design patterns:

- For a known embodiment, it can reuse pretraining normalization statistics to
  preserve the coordinate convention expected by a pretrained model. This is a
  transfer/compatibility mechanism, not a way to create behavioral
  generalization, and it is not required for the numerical fix here.
- Its ALOHA data configuration defaults to delta joint actions for both arms,
  with absolute gripper actions. At inference it adds the current state back.

Those patterns fit this case better than removing left-arm dimensions.

### Original ACT / ALOHA

The original ACT loader keeps the whole bimanual qpos/action vector but clamps
both qpos and action standard deviations to at least `1e-2` in their native
units. That prevents a stationary joint from becoming a million-gain input.

### Diffusion Policy

Diffusion Policy detects ranges or standard deviations below `1e-4`. It assigns
unit scale and centers those dimensions instead of dividing by their empirical
near-zero spread. Again, the dimension stays in the contract.

### Octo

Octo supports per-dimension normalization masks and a robust bounds mode using
the 1st/99th percentiles. Bounds-mode inputs are clipped to `[-1, 1]`, preventing
unbounded normalized values. Its plain mean/std mode still has the same small-
denominator risk unless the metadata mask is configured appropriately.

No single framework supplies the whole solution. The recurring robust patterns
are scale floors, bounded inputs, consistent train/inference transforms,
relative actions where “hold current pose” matters, and explicit diagnostics.

## Recommended repair for this project

1. Keep all 48 bimanual state dimensions and all 16 action dimensions.
2. Continue deriving centers and empirical spreads from the actual training
   dataset, but replace Flow S1's `1e-6` fallback with non-explosive effective
   scales. A direct baseline is the previous Pi0.5 quantile rule; a production
   version should configure separate physical floors for position, velocity,
   torque, and action fields.
3. Use exactly the same saved effective scales for training, inference, and
   action inversion.
4. Convert arm joint actions to deltas/residuals relative to current state while
   retaining absolute gripper semantics, unless a controlled comparison proves
   absolute actions are required. This makes a stationary arm target zero
   movement rather than one memorized pose.
5. Add state jitter at measured encoder-noise scale during training and require
   a perturbation test. This regularizes local sensitivity but does not replace
   genuine posture coverage.
6. Include diverse initial bimanual postures or relevant multi-task data if the
   policy must adapt behavior based on the left pose. Such data supplies
   behavioral coverage; it is separate from normalization and generic
   calibration motion is not automatically task supervision.
7. Fix episode-boundary construction and retrain from scratch. Existing weights
   learned from both the unsafe normalization and corrupted chunks.
8. Before another long run, require held-out episode loss, state/image shuffle
   sensitivity, and episode-boundary chunk reconstruction as training gates.

Exact numerical floors should be based on OpenArm2 units, sensor resolution,
and acceptable physical gain. ACT's `1e-2` and Diffusion Policy's `1e-4` are
evidence for the pattern, not values to copy blindly across radians, degrees,
velocity, and torque.

## Literature interpretation

Behavior cloning only constrains the policy on demonstrated states. The DAgger
analysis formalizes how deployment enters the learner's own state distribution,
where errors compound. Here, near-zero normalization artificially turns a tiny
physical deviation into an enormous distribution shift.

Input noise augmentation is a principled local regularizer: classical results
relate training with noise to a derivative-smoothing/Tikhonov penalty. For this
case, encoder-scale jitter can discourage arbitrary sensitivity near a held
pose, but it cannot teach task behavior at genuinely different arm postures.

## 2026-08-05 30k training-failure proof (superseding runtime mitigations)

The current investigation treats command clamps, rate limits, and deployment
gates as out of scope: they cannot make a wrongly trained policy correct.  The
question here is why the new 30k checkpoint learned the wrong conditional
distribution and what the next training run must change.

### The 30k checkpoint learned the episode-boundary corruption

The training adapter checked only the legacy `episode_data_index` attribute.
Current LeRobot v3 datasets expose episode membership through the
`episode_index` Hugging Face column instead, so all 40,101 rows were treated as
one continuous episode during this run.  The fixed adapter now resolves 241
episodes from that column and pads each chunk at its own episode end.  A
regression test using the current v3 contract fails on the old implementation
and passes on the fix.

This was not merely dormant bad code.  Eight exact training observations were
selected 15 frames before episode ends.  For each one, the 30k checkpoint's
predicted 50-step chunk was compared with (a) the label the buggy loader used,
which continues into the next demonstration, and (b) the correct label, which
pads the current episode's final action.  Mean tail MAE was:

- buggy cross-episode label: **0.513 degrees**;
- correct padded label: **6.780 degrees**;
- mean disagreement between those labels: **6.731 degrees**.

Thus the checkpoint reproduced the cross-episode reset sequence roughly 13
times more closely than the correct target.  The boundary bug is visibly
imprinted in the weights and this checkpoint cannot be repaired by changing
inference settings.

### The 30k checkpoint also learned to ignore proprioceptive state

A deterministic high-noise flow-loss audit used eight training frames spread
across the 241 episodes and four fixed noise seeds.  At `t=0.95`, almost all
action information has been removed from the noisy action input, so the
observation context must identify the target.  Only the conditioning input was
changed:

| conditioning | mean loss | change from correct |
| --- | ---: | ---: |
| correct images + state | 0.002430 | baseline |
| state shuffled across samples | 0.002422 | -0.33% |
| state set to zero | 0.002443 | +0.50% |
| all camera images shuffled | 1.679845 | +69,019% |
| images and state shuffled | 1.680993 | +69,067% |

The normalization floor therefore did what it claimed numerically, but had no
behavioral leverage: the optimizer found a lower-effort image-to-action
memorization solution and the aggregate training loss did not penalize it.
This agrees with the live-frame counterfactual, where replacing the complete
48-D state changed the action chunk by less than 0.2 degrees while replacing
images changed active-arm outputs by many degrees.

The architecture makes this shortcut easy: three cameras contribute 768 DINO
patch tokens, while the complete 48-D proprioceptive vector contributes one
state token.  More importantly, absolute joint targets do not mathematically
require the state input when image appearance already correlates with pose.
No logged metric checked otherwise.

### Consequence for the next training run

Another normalization-only retrain is rejected.  The minimum causal A/B is:

1. fix episode boundaries and train/validate by whole episode, never by random
   frames;
2. add the deterministic state/image shuffle audit to every saved checkpoint;
3. compare boundary-fixed absolute actions against boundary-fixed relative
   joint actions (`target_position - current_position`) with all 16 action
   dimensions retained;
4. compute relative-action statistics over valid action chunks rather than only
   one-step frame pairs, and invert them with the current raw state at inference;
5. require the relative model's first decoded absolute action to move with a
   counterfactual current state, while its predicted residual remains stable;
6. do not start another 30k run until a short probe passes boundary-label,
   held-out-episode, modality-sensitivity, and first-action anchoring checks.

The two defects explain different parts of the observed behavior.  State
ignorance explains why a live arm at about 31.7 degrees can receive a first
target near 45 degrees based mainly on image resemblance.  Boundary corruption
explains why chunks near demonstrated episode tails deliberately predict the
next demonstration's reset.  They coexist in the same 30k checkpoint; neither
is an inference-rate issue.

### Additional dataset and RTC exclusions

The 0803 demonstrations are not dominated by stationary chunks.  Across all
40,101 frame-aligned 50-step chunks, only 2.63% have less than one degree of
maximum right-arm displacement; none of the 241 episode-start chunks do.  The
median 50-step maximum displacement is 25.14 degrees.  Therefore the observed
stuck/oscillatory behavior is not explained by a large majority class of
"stop" chunks, and filtering low-motion chunks is not the first treatment.

The immediate action/state residual does vary by task phase.  For
`right_joint_4.pos`, the 241 exact episode starts have p99 4.89 degrees, maximum
7.67 degrees, and zero samples above 10 degrees.  Across all task phases the
p99 is 11.71 degrees and the maximum is 26.74 degrees.  The live start's roughly
13.7-degree command therefore looks like a mid-episode action selected for a
start observation, consistent with image-only phase/posture aliasing.

The training-time RTC construction matches the cited method after accounting
for this implementation's reversed flow-time convention: the paper places
clean data at flow time 1, while this implementation places clean data at time
0.  Ground-truth prefix tokens from the same chunk, postfix-only loss, and a
random delay are the intended method.  RTC remains worth auditing for handoff
quality, but it is not changed in the next causal training comparison.

### Implemented training prototype

The worktree now contains an opt-in `use_relative_actions` Flow S1 contract:

- all 16 action dimensions and all 48 state dimensions remain present;
- the 14 non-gripper `*.pos` action targets are encoded relative to the current
  state position with the same feature name;
- both gripper targets remain absolute;
- the interleaved position/velocity/torque state layout is resolved by name,
  never by assuming the first 16 state values are positions;
- relative normalization statistics cover all valid within-episode chunk
  tokens and exclude padded tails;
- inference and RTC prefixes use the same current-state anchoring before action
  denormalization/inversion.

Training now also supports a deterministic whole-episode validation split.  By
default 10% of episodes are excluded from optimization, normalization stats are
fit on training episodes only, and a fixed held-out flow loss is recorded with
every checkpoint.  This closes the earlier adjacent-frame/overlapping-chunk
leak that would make a random frame validation split meaningless.

The GUI exposes `Relative arm actions`, and the local training image
`lerobot-training:dev-local` was rebuilt from this source.  The next run should
be a short fail-fast probe using this image and the relative option, not another
normalization-only 30k run.
