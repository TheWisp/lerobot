# External RGB-D workflow probe

The [YCBInEOAT real-robot sugar-box sequence](https://github.com/wenbowen123/iros20-6d-pose-tracking) was already cached for tracker benchmarking. We used source frames 619–649 (31 frames, 1.67 s), outside the two FLASH demos. The source supplies RGB, aligned depth, camera intrinsics, object masks and annotated object poses. This probe did not use an object mesh as tracker input.

`benchmarks/flash_import_external_rgbd.py` imported the frames as an ordinary local LeRobot episode at `/home/feit/.cache/huggingface/lerobot/demos/flash_external_ycb_sugar_observation`. Its `flash/v1/source.json` preserves provenance, intrinsics and the fact that the episode is **perception-only**. Original irregular timestamps and frame indices are explicit per-frame features. The standard dataset's nominal video rate is 18 fps. Readback checked frames 0, 15 and 30: all no-return depth pixels remained zero and the 99th-percentile valid-depth difference was 1 mm. The default depth-video minimum would instead have changed zero to 10 mm; this import sets the minimum to zero because the source's zero means invalid.

We ran the shared `SurfaceTrackingSession` through all 31 imported frames, once with the dataset's masks and once with a point-seeded SAM3 mask. SAM3's median mask intersection-over-union with the supplied masks was 0.669. Both tracker runs emitted a fitted pose on all 30 subsequent frames, but independent object-pose labels show that **emitting a pose is not the same as getting it right**:

| Masks    | Median orientation error | Median observed-patch center error | Median reverse depth disagreement |
| -------- | -----------------------: | ---------------------------------: | --------------------------------: |
| Supplied |                    14.2° |                            10.4 mm |                           11.4 mm |
| SAM3     |                    15.6° |                             7.1 mm |                           12.5 mm |

The orientation error remains with supplied masks, so SAM3 segmentation alone cannot explain it. This short sequence is a generalization failure to investigate, not evidence that a transferable skill was prepared. [The side-by-side video](sugar-box-external-tracking.mp4) compares the projected FLASH patch with the dataset's pose label on identical RGB frames; green traces the SAM3 mask. It runs slower than the source for inspection.

The normalized clip has no imported robot actions, measured tool trajectory or camera-to-robot transform. The original ROS bag has gripper transforms, but its camera and robot frames are disconnected in the recorded transform tree. This **only removes gripper-backed pose prediction and executable action extraction**. Vision, object masks, causal scene points, object–object observations and key-frame/adaptation annotation do not require robot actions. Camera coordinates are used explicitly until calibration is available.

`benchmarks/flash_extract_observation_rgbd.py` runs the imported episode through the same `SurfacePoseBackend`, `extract_pose_trace`, `CausalPoseService`, and `SceneEvidenceWriter` used by FLASH preparation. It uses the saved rig configuration as an explicit comparison input, rather than tuning a threshold for this clip. The extractor now accepts either saved mask directories or SAM3 labels and image clicks. We used `--prompt 'sugar_box=sugar box' --seed sugar_box=360,160 --prompt 'can=white bottle' --seed can=307,316` to process both objects **without supplying source masks**. The clicked pixels were chosen on the RGB frame; annotated object poses were used only afterward to score the result. Run → FLASH → Demos lists this **RGB-D observation** and plays both objects, their masks, predicted poses and scene support in the ordinary camera and 3D review views. It does not label the episode as a runnable skill.

The same replay now has **Track objects**. In the browser, we reopened this episode, kept its two object descriptions and first-frame clicks, started the shared processing worker, and saw the completed result reload in place. The worker took about 15 seconds for 31 frames on this machine. A failed or interrupted pass keeps the previous complete evidence. The processing parameters are editable and saved by content hash; the UI job status survives the generic run-status cleanup. This establishes the processing and review path for an already imported RGB-D dataset, not a one-click importer for arbitrary online video files.

On 2026-10-29, a repeat extraction found a clock error in the saved pose evidence: offline fitting stamped availability with the later process's monotonic wall clock (about 751,000 s) while source frames used episode time (0–1.67 s). The source-order extraction now records each proposal and accepted estimate at the corresponding frame's recorded availability and retains its source frame and object-frame version. A 31-frame sugar-box/can re-extraction produced availability from 0 to 1.674 s; all 62 role/frame evidence outcomes and estimators matched the previous pass, with no pose translation shift above 0.01 mm. This is an offline causal convention, not a claim that the same computation met live deadlines. Older evidence remains readable; rerunning extraction writes the new provenance fields.

[The earlier recorded UI playback](observation-ui-sugar-can.mp4) shows the same two-object viewer with saved masks at one-third source speed for inspection; the current replay uses SAM3 masks produced directly during extraction. The video is not a claimed successful robot action.

The same playback now has **Edit relationships**. In a headless Chromium test on this dataset, we marked two review key frames, saved and reloaded them, added a second object–object relation at one frame, then removed it without disturbing the first. In the 3D view we picked a point on the can's measured surface; the editor retained its local point, normal and whether the underlying pose was observed. The [editor capture](observation-relationship-editor.png) shows the scene, key-frame list and evidence labels at source frame 619. This permission was tested as a draft and not saved for the clip, since no contact event justifies it.

The sugar box moved about 170 mm and 9° over the clip. With source masks, it had one directly accepted pose at its first frame; all 30 later accepted poses came from causal object-point motion. After aligning the first frame, its transported first-view surface had **1.7 mm median error and 0.5° median orientation error** against independent object-pose labels; every later frame was within 10 mm and 10°. The rejected direct surface fits had 13.5 mm and 14.2° median errors. The **direct SAM3 extraction now shown in the UI** likewise accepted one first-frame pose and 30 point-motion predictions, with **1.8 mm median surface error and 1.1° median orientation error**, all 30 within 10 mm and 10°. This checks within-episode motion, not absolute pose or cross-episode correspondence. It is evidence that a labeled RGB-D episode can use the shared pipeline without source masks, but does not establish performance under contact occlusion.

We also imported a second, independent YCBInEOAT sequence, `cracker_box_yalehand0` frames 1253–1283, as `/home/feit/.cache/huggingface/lerobot/demos/flash_external_ycb_cracker_observation`. It is more occluded (29% labeled point visibility). Before the fix, the causal estimator kept publishing its first **stationary** pose for the entire moving interval; by the last frame that pose was 814 mm and 49° from the labels. The rejected raw fits were worse (1126 mm median surface error). The generic fix tests the previously measured surface against current aligned depth whenever a direct fit is lost and a stationary prior is active. At frame 1, 436 projected pixels had reliable depth and 98% showed free space behind the old predicted surface. The estimator now marks the pose unknown at that frame and remains unknown for the rest of this clip. It avoids a false pose; it **does not recover the moving object's pose**. A future tracker must reacquire it from new visual evidence.

`benchmarks/flash_score_observation_rgbd.py` reproduces both label comparisons from the saved observation evidence without feeding labels into extraction. Run → FLASH → Demos now keeps a lost-pose status in the replay and says when measured depth ruled out the old position. No environment relationship became verified in either sequence. These clips validate the shared observation-only pipeline and editing path, **not** a contact-rich interaction or an adaptation policy. A full action-workflow test needs robot actions/tool pose and calibrated camera-to-robot geometry; [RH20T's published API](https://github.com/rh20t/rh20t_api) describes those fields.
