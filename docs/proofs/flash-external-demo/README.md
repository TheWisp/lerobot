# External RGB-D workflow probe

The [YCBInEOAT real-robot sugar-box sequence](https://github.com/wenbowen123/iros20-6d-pose-tracking) was already cached for tracker benchmarking. We used source frames 619–649 (31 frames, 1.67 s), outside the two FLASH demos. The source supplies RGB, aligned depth, camera intrinsics, object masks and annotated object poses. This probe did not use an object mesh as tracker input.

`benchmarks/flash_import_external_rgbd.py` imported the frames as an ordinary local LeRobot episode at `/home/feit/.cache/huggingface/lerobot/demos/flash_external_ycb_sugar_observation`. Its `flash/v1/source.json` preserves provenance, intrinsics and the fact that the episode is **perception-only**. Original irregular timestamps and frame indices are explicit per-frame features. The standard dataset's nominal video rate is 18 fps. Readback checked frames 0, 15 and 30: all no-return depth pixels remained zero and the 99th-percentile valid-depth difference was 1 mm. The default depth-video minimum would instead have changed zero to 10 mm; this import sets the minimum to zero because the source's zero means invalid.

We ran the shared `SurfaceTrackingSession` through all 31 imported frames, once with the dataset's masks and once with a point-seeded SAM3 mask. SAM3's median mask intersection-over-union with the supplied masks was 0.669. Both tracker runs emitted a fitted pose on all 30 subsequent frames, but independent object-pose labels show that **emitting a pose is not the same as getting it right**:

| Masks    | Median orientation error | Median observed-patch center error | Median reverse depth disagreement |
| -------- | -----------------------: | ---------------------------------: | --------------------------------: |
| Supplied |                    14.2° |                            10.4 mm |                           11.4 mm |
| SAM3     |                    15.6° |                             7.1 mm |                           12.5 mm |

The orientation error remains with supplied masks, so SAM3 segmentation alone cannot explain it. This short sequence is a generalization failure to investigate, not evidence that a transferable skill was prepared. [The side-by-side video](sugar-box-external-tracking.mp4) compares the projected FLASH patch with the dataset's pose label on identical RGB frames; green traces the SAM3 mask. It runs slower than the source for inspection.

The normalized clip has no imported robot actions, measured tool trajectory or camera-to-robot transform. The original ROS bag has gripper transforms, but its camera and robot frames are disconnected in the recorded transform tree. This **only removes gripper-backed pose prediction and executable action extraction**. Vision, object masks, causal scene points, object–object observations and their future key-frame/adaptation annotation do not require robot actions. Camera coordinates are used explicitly until calibration is available.

`benchmarks/flash_extract_observation_rgbd.py` now runs the imported episode through the same `SurfacePoseBackend`, `extract_pose_trace`, `CausalPoseService`, and `SceneEvidenceWriter` used by FLASH preparation. It uses the saved rig configuration as an explicit comparison input, rather than tuning a threshold for this clip. We added a SAM3 mask for the stationary can to exercise multi-object processing; the sugar box uses the source mask. Run → FLASH → Demos lists this **RGB-D observation** and plays both objects, their masks, predicted poses and scene support in the ordinary camera and 3D review views. It does not label the episode as a runnable skill.

[The recorded UI playback](observation-ui-sugar-can.mp4) shows this two-object evidence at one-third source speed for inspection; it is a browser capture of the actual FLASH review view, not a claimed successful robot action.

The result exposes a limit: each object had one directly accepted pose at its first frame. Over the remaining 30 frames, the sugar box used causal object-point motion; the can used stationary or object-point prediction. No environment relationship became verified. Direct proposals had roughly 10–14 mm reverse depth disagreement against the saved 5 mm acceptance setting, so the system withheld them. This clip shows an object moving relative to another, but no contact; it does **not** validate interaction-key-frame editing or an adaptation policy. A later full action-workflow test needs robot actions/tool pose and calibrated camera-to-robot geometry; [RH20T's published API](https://github.com/rh20t/rh20t_api) describes those fields.
