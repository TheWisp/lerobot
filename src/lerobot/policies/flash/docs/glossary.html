FLASH tracking glossary

Definitions for the current growing-surface tracker and its recovery experiments. Each entry names the corresponding code. These definitions describe what the system stores or computes; they do not certify that an estimate is correct.

Writing convention: use the names below and link their first use in an explanation or report. Qualify “identity,” “reference,” and “alignment.” Define a new term here before introducing it elsewhere. Explanations must also stand on their own for remote readers who cannot open local links. Specify 2D or 3D, the coordinate system, and separate position from rotation differences.

Checked against production source at 9ff25cf80 and the recovery experiments at 77becade1. Experimental recovery is explicitly identified below; it is not the production default.

Point track ID

An integer label carried by a tracked image point across processed frames. For example, ID 42 labels a pixel in one image and the pixel that the matcher assigns to it in the next image. This represents a hypothesis that both pixels show the same physical point; tracking can be wrong.

The shared tracker keeps the ID when it accepts the next match. A newly selected point receives a new ID. Matching an older accepted image through the stored history requires IDs shared with the current frame.

Earlier wording: “image identity” meant this point track ID. It did not mean the image's frame number or the selected object's identity. “All old point tracks were lost” can be true while SAM still finds the object.

Code: SharedFrameTracker._seed assigns IDs; update carries them; pairs joins surviving IDs.

Image match / 2D correspondence

A proposed pairing of a pixel in a source image with a pixel in a target image. LK and UFM supply these pixel pairs. An accepted image match has passed the matcher's checks; it does not yet establish a valid 3D measurement or the physical identity of the object.

A pair can be computed directly between two images without retaining a point track ID through every intervening frame. The recovery benchmark's fresh-rematching experiment does this when too few usable 3D pairs remain.

Code: SharedFrameTracker.update; experiment: flash_motion_recovery.py, rematch policy.

Usable and validated 3D pairs

A usable 3D pair is an image match whose two pixels have suitable mask membership and depth support, converted to two 3D positions. Each position uses its image's camera intrinsics and depth. “Validated pairs” in the recovery report are the subset retained by the robust rigid-motion fit.

These are separate stages: a match can survive in 2D but lack usable depth; a usable 3D pair can still disagree with the other points' motion. Neither stage proves that the pixels depict the same physical surface point.

Code: SharedFrameTracker.pairs, measured_pairs, and robust_fit.

Segmentation mask

A per-image set of pixels estimated to belong to the selected object. In these experiments the masks are saved SAM outputs, aligned to the recorded RGB and depth. A mask selects the current object region; it does not pair old and new pixels or specify the object's 3D rotation.

Code: SharedFrameTracker.update checks mask dimensions; pairs checks source and target mask membership.

Object coordinates and pose

Object coordinates are the fixed 3D coordinate system used to store the object's reference surface. Its pose is the rotation and translation mapping those coordinates into the current camera's coordinates. The code stores this as a 4×4 transform, camera_from_reference.

For a stored point p, its predicted camera position is R × p + t. The coordinate origin stays fixed when the surface grows; it need not be the object's physical centre. Here “reference coordinates” means this coordinate system, not a particular saved image.

Code: SurfacePatch.points converts measured camera points into reference coordinates; PoseKalmanFilter uses a fixed object point.

Stored surface / surface map

The accumulated 3D surface measurements stored in object coordinates. New accepted views can add measurements of newly visible parts. The current visible surface is separately measured from the current mask and usable depth. Neither is a complete ground-truth model of the object.

Code: SurfacePatch and SurfaceStore.

Local surface fitting

Moving and rotating stored 3D surface points to agree with the object's currently measured 3D surface points. This is also called surface registration. The starting estimate has two distinct parts: position (where the object is) and orientation (how it is rotated).

“Local” means the solver improves an initial estimate using spatially nearby 3D points and a limited number of iterations, rather than searching every possible position and rotation. A wrong starting position, a wrong starting rotation, or both can prevent a successful fit. A rotation can move surface points away from their corresponding measured points even if the object's centre stays in the same place.

Earlier wording: “too far away” failed to distinguish those cases. In cube frame 2741, comparing the original starting estimate with the recovered fit, the mean position of the same stored surface points changes by 44.9 mm, and orientation changes by 2.7°. These compare two estimates, not errors against a known correct pose. Changing the starting estimate helps this example; it does not isolate the separate causal effects of position and rotation. The SAM mask and depth are identical in both trials. See the measured comparison.

Implementation defect, checked separately: the current path does not first align the two surface centres. In a controlled replay of the same frame, changing only the initial translation to align the means removes a 43.4 mm centre gap. The starting rotation changes by 0°, and the same fit and checks then accept the result. Aligning medians also succeeds. Spatial displacement alone should not be presented as an inherent recovery limitation when this initialization is missing. The solver's internal coordinate centring preserves the initial displacement; it does not perform this correction. Controlled trial evidence.

Code: GrowingSurfaceSession.update chooses the starting pose; WholeSurfaceFit._solve and fit_once run one bounded fit; LibraryMatcher.refine supplies the correspondence-distance and iteration limits.

Object point anchor

A remembered 3D position of a point on the object, measured relative to the object's fixed coordinate system. Its stored value is three coordinates in metres. The label “anchor” names a code data structure; it is not an extra physical marker.

For example, consider a small visible spot on a cube:

  1. In the RGB image the spot has a 2D pixel position, such as (u, v). The image tracker gives that track an integer ID.
  2. Depth at that pixel and the camera calibration give a 3D position relative to the camera.
  3. Using the accepted object position and rotation, the code expresses that 3D point relative to the object and remembers it under the track's ID: anchors[42] = (x, y, z).

The remembered value is 3D; the associated image track has 2D pixel positions. When the cube moves, the spot's camera coordinates change, while its stored coordinates relative to the cube remain fixed. Later measurements with that track ID can be associated with this remembered point. An ID match remains a tracking hypothesis and can be wrong.

The entry can remain stored without a current measurement of the spot. That does not establish that the spot is physically occluded or that its predicted current position is correct. Within the same object reference, accepted observations can add new entries but do not move existing entries.

Code: ObjectGroupAssociation.record_observation creates entries and preserves existing coordinates; query uses them and can add points through an established group relation. Group-local anchors in motion_groups._Group use a different coordinate system.

Motion group

A collection of 3D points that the tracker assumes move together as one rigid body. This means one common rotation and translation explains their motion; their distances from one another stay approximately constant. The group need not equal one physical object or one SAM mask.

For example, points on a tray and a cube resting on it can appear to move together. If the cube is then lifted, that shared-motion assumption is no longer valid for the cube. Tracking the tray successfully does not tell us where the lifted cube went.

The implementation retains some unmeasured group points and predicts their positions from the measured members. Remembered object points can connect an object to such a group. In the recorded failure, the group still had measured background points while its established object points had no current measurements, so its object position prediction was stale.

Code: GroupView and ObjectGroupAssociation.query.

Pose prediction / prior

An estimate of the current pose before accepting the current object's surface measurement. The Kalman filter carries the previous pose through camera changes and any usable measured group motion. A group can also supply a separate pose hint through the stored object-to-group relation.

A prediction and a fit's starting pose need not be the same: the starting pose can instead come from current image matches. Publishing a predicted pose does not mean the object was measured this frame.

Code: PoseKalmanFilter.predict, ObjectGroupAssociation.query, and GrowingSurfaceSession.update.

Kalman pose update

Combining the predicted pose with a new surface-fit pose using their estimated uncertainty. The output is called the fused pose. Rotation and position can receive different corrections according to the information supplied by the measurements.

Earlier wording: “smoothing” referred to this pose update, not blurring RGB, masks or depth. The fused pose can differ from both input poses, so it must pass the geometry checks again. In the ring example a fit passes, but the fused pose fails and the correction is rolled back.

Code: PoseKalmanFilter.correct and _correct; GrowingSurfaceSession.update checks the fused pose. Ring evidence.

Accepted observation / reference image

A processed RGB-D image and mask whose pose the tracker accepted for its state update. The tracker retains that observation, its frame ID, intrinsics and pose for subsequent matching. “Reference image” in the recovery report means this last accepted image.

The last accepted image may be older than the previous processed image. Accepting a newer image does not redefine the fixed object coordinates. “Accepted” reports the estimator's decision; it is not independent ground-truth verification.

Code: GrowingSurfaceSession._remember_observation stores accepted_frame, accepted_pose, and accepted_observation.

Tracking loss and recovery

Recovery means obtaining an accepted current object pose after the tracker could not obtain one. Specify what was lost: old point tracks, the mask, usable depth, or an accepted pose. Those are different failures.

The compact complete-loss test deliberately supplies one black image with empty mask and depth, then restores recorded observations. It checks recovery without surviving old image tracks. The fresh-rematching experiment computes new matches from the last accepted image; it does not restore the old IDs.

Evidence: recovery report; code: test_recorded_motion_recovery.py and flash_motion_recovery.py.
